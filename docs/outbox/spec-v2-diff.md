## v2.0.1 のあとに残った食い違い（spec は直していない）

### F1. §10.1 の Diver の行

- **条項**：§10.1 の表「Diver CLI / SDK … OSS（`npx ludion`、`@ludion/diver`）」。
- **現状**：決定2で、SDK は `ludion/diver`（§10.3、§13.2 は v2.0.1 で直した）。
- **提案**：§10.1 の `@ludion/diver` を `ludion/diver` にする。

### F2. §22 の個人情報

- **条項**：§22「Gate が外に出すのはメタデータだけだ。IP は切り詰めて塩付きハッシュにする」。
- **現状**：決定4で、IP のハッシュは外に出さない（1時間ごとの集計だけ）。
- **提案**：§22 を「Gate が外に出すのは1時間ごとの集計だけで、IP もそのハッシュも出さない」にする。

### F3. §8 不変条件6

- **条項**：「送るのはメタデータだけで、本文・クッキー・クエリの値・申告の文は送らない」。
- **現状**：決定4の集計も「メタデータ」の一種なので矛盾はしない。ただし、より強い形（集計だけ）が §12.9 にしかない。
- **提案**：§8 は人間だけが変えられるので、変えるかどうかの判断だけ。変えないなら、このままでよい。

### F4. §10.1 の Ludion Cloud の行、§11.13 の評判イベント

- **条項**：§10.1「Ludion Cloud：メタデータの受信」、§11.13「評判イベント…証拠は受領証のハッシュ」。
- **現状**：決定4のあと、Cloud が受け取るのは1時間ごとの集計。評判イベントは来訪ごとの事象なので、集計と別の道になる。
- **提案**：評判イベントは Gate 300 まで凍結の範囲（Depth の段階）に近いので、ローンチでは作らない。作る時に ADR-038 の「見直す条件」で扱う。

## A. spec の差し替えで、既存のオラクルを落とさないためにこのコミットでしたこと

spec の差し替えで、ラチェット済みの WEB-3 と WEB-2 が FAIL になった（v1.0.1 の節番号を読んでいた）。spec を変えずに、検証器とサイトの側を v2.0 に合わせた。緩めたオラクルはない。

### A1. エラー応答の表（§11.12）

- **条項**：§11.12 エラー応答。v2.0 で `purpose_required` と `blocked_by_site` が加わり、11件になった。表は §10.11 から §11.12 に移った。
- **現状**：
  - WEB-3 は表を「`### 10.11` から `### 10.12` まで」で切り出していた。v2.0 では0件になり、FAIL。
  - Gate（`ERRORS`）は8件で、新しい2件をまだ返さない。
- **このコミットでしたこと**：
  - WEB-3 は表を、節の番号ではなく見出し「エラー応答」で探すようにした。表が見つからなければ落ちる（前と同じ）。
  - 新しい2件の help のページ `/e/purpose_required` と `/e/blocked_by_site`（英日）を足した。中身は §11.7 と §12.4 のとおりで、「オープンソースの Gate は、まだこれを返さない」と書いた（`rate_limited` と同じ扱い）。
  - 一覧のページ（`/e`、`/ja/e`）に2行を足した。
  - WEB-3 は11件 × 英日 = 22ページで PASS。
- **提案**：新しい2ページの文面を読んでほしい。公開する文面になる（`/e/<code>` の文面の確認は、すでに人間待ちにある）。

### A2. サイトが引く spec の節（WEB-2 の出所）

- **条項**：
  - §11.4 リクエストの署名
  - §11.5 Staple
  - §11.11 失効
  - §14.5 Depth
  - §15 Ballast
  - v1.0.1 ではそれぞれ §10.4、§10.5、§10.10、§13.4、§14 だった。
- **現状**：
  - サイトの数字の出所のリンク（16か所）は、v1.0.1 の見出しのアンカーを指していた。WEB-2 はアンカーの節の中に数字があるかを確かめるので、FAIL になった。
  - WEB-2 と速いテスト（`copy.test.mjs`）の仕込みも、v1.0.1 のアンカーと文言（「24時間以内」）を使っていた。
- **このコミットでしたこと**：
  - リンクとその表示（spec §10.4 → §11.4 など）を、v2.0 の節に向け直した。数字は全て、v2.0 の節にもある（60秒、3600秒、±30秒、最長1時間、90日、24時間）。
  - テストの仕込みも、同じ節と v2.0 の文言（「24時間で応じる」）に向け直した。
  - WEB-2 は PASS。仕込み 21/21 を捕まえ、対照 5/5 は指摘なし。
- **提案**：なし。ただし次の A3 を見てほしい。

### A3. Depth の表の中身（サイト）

- **条項**：§14.5 の D3 は「D2 に加え、90日の行動履歴が健全」、D4 は「D3 に加え、Ballast の保証と外部監査」。
- **現状**：`/e/depth_insufficient`（英日）の D4 は「D3 plus 90 days without incidents and a third-party audit」。数字（90日）は §14.5 にあるので WEB-2 は通る。しかし、90日が D3 の条件か D4 の条件かが、spec と食い違う。
- **提案**：サイトの Depth の表を §14.5 に合わせる。D2〜D4 は §9.5 で凍結（画面に出さない）なので、表から消すのも手。どちらにするか決めてほしい。

### B4. npm の公開（§20.2、§25 Q17、§10.3）

- **条項**：
  - §20.2「npm に `ludion` を公開済み（Trusted Publishing）」

  - §10.3「公開するパッケージは最小にする。CLI の `ludion` と、Gate を1つ（`@ludion/gate` に node・next・workers のサブパスをまとめる）」

- **提案**：
  - §20.2 を「最初の版は手で公開し、以後は Trusted Publishing」にする。
  - `@ludion/gate` に1つにまとめるかを決めてほしい。まとめるなら、PUB-1/2 の公開セットと docs/PUBLISH.md の表を変える（緩めるのではなく、セットを置き換える）。

## C. spec と、既存の設計・コード

### C1. 設定ファイルの名前と項目（§12.7）

- **条項**：§12.7 の設定例は `ludion.yaml`。`decisions`（止める判断）、`routes[].writes: false`、`require.purpose` を持つ。
- **現状**：
  - 設定は `ludion.config.json`（ADR-022）。YAML の読み込みはない。
  - トップの項目は `site_id`、`pressure`、`routes`、`report`、`fail_mode`、`timeout_ms`、`friction_hook`、`trust_proxy`、`authorities`、`registry`、`categories`、`mandate_ledger`。
  - `decisions` と `writes` と `purpose` はない。
- **提案**：
  - 形式は JSON のまま（ADR-022。依存を増やさない）にして、spec の例を JSON にする。`decisions` などは BLK-1 と PUR の実装で足す。
  - 形式を YAML にするなら、ADR-022 を置き換える ADR が要る。

### C2. 名札（Card）の中身（§11.2）

- **条項**：例は `token_endpoint_auth_method: "private_key_jwt"` を持ち、`ludion` オブジェクトは `diver`、`operator.verified`、`commitments`。
- **現状**：
  - `cardDocument()` は `client_id`、`client_name`、`contacts`、`jwks_uri`、`web_bot_auth`、`ludion: { version, diver_id, registry, root_kid }` を出す。
  - `token_endpoint_auth_method` はない。`ludion` の中の名前（`diver_id` と `diver`）が違う。
- **提案**：
  - MCP-1（Keycloak の CIMD）で要る項目を確かめてから合わせる。Q19（`redirect_uris` と localhost）と同じ作業。
  - `ludion` の中の名前はどちらかにそろえる（DIV-2 のテストも合わせる）。

### C3. 来訪ごとのメタデータ（§12.9、PRIV-4、不変条件15）

- **条項**：不変条件15「AI の行動は、運営者単位の集計でしか外に出さない」。PRIV-4「利用者起点の来訪ごとの経路は、Gate の外に出ない」。
- **現状**：Gate は、リクエストごとのメタデータのイベント（時刻、経路のテンプレート、分類、判定、diver_id など）を Ludion Cloud に送れる（`send_metadata: true`、PRIV-1 で中身を検査）。来訪ごとの経路が外に出ている。
- **提案**：
  - PRIV-4 を通すには、Gate の中で集計してから送る形に変える。朝のレポート（`ludion report`）の入力も変わる。
  - 「利用者起点の来訪」の線引き（署名した AI の行為は来訪ごとに出してよいか）を決めてほしい。

### C4. 朝のレポート（§12.3、ONE-2）

- **条項**：「数字は一つ、判断も一つ」。見出しは名乗った相手と名乗らない相手の比率。
- **現状**：`ludion report`（RPT-1）は、重要経路の数、北極星（Verified Actions）、分類別、経路別などの複数の節を出す。大きな数字が2つある。
- **提案**：ONE-2 の実装で、見出しの数字1つと判断1つの形に作り直す。RPT-1 の正解（数字が正しいこと）は残す。

### C5. 目的の申告（§11.7、PUR-1〜6）

- **条項**：`Ludion-Purpose` の読み取り、照合、`note` の扱い、diver の送信前フィルタ。
- **現状**：Gate にも diver にもまだない。
- **提案**：なし（PUR-1〜6 を PENDING で足した）。§11.4 の署名の例は `ludion-purpose` を署名の対象に含めている。STD-2 と GATE-7 に、申告の差し替えの攻撃を足す。

### C6. init の体験（§9.2、§13.1）

- **条項**：
  - `npx ludion init` から60秒で「あなたの AI の名前：https://dvr-….agents.ludion.ai」。
  - Web と MCP の使い方を一画面で見せる。
  - バッジ、最後の任意の1問（MCP／Web／消せるから／その他）。
  - Root 鍵の保管先として KMS、キーチェーン、ファイルを選べる。
- **現状**：
  - `init` は Root 鍵を封をしたファイルに置く（ADR-019。KMS とキーチェーンはない）。
  - `register` と `revoke`（`--compromised` あり）は Registry に対して動く。
  - Card Host（`@ludion/card-host`）は手元で動く。
  - `*.agents.ludion.ai` は、まだどこにも出ていない。2段目のワイルドカードの証明書の判断（お金）が人間待ち。
  - バッジと1問はない。
- **提案**：
  - §9.2 の1画面目は、Card Host の本番の置き場所が決まるまで出せない。証明書の判断を、ローンチの条件に入れる。

### C7. 名簿の事前登録（§14.2）

- **条項**：主要10件を、公開情報から先に載せる。
- **現状**：名簿（`services/registry`）は登録された Diver だけを持つ。事前登録の仕組みも、10件のデータもない。宣言台帳（レーン2の tracecheck）はある。
- **提案**：ローンチの範囲（§9.4）に入っていないので、ローンチ後（§20.4 の4）に回す。オラクル（例：REG-6 事前登録の名札は「本人の確認前」と明示され、鍵は各社の公開物を指すだけ）は、その時に足す。

### C8. 不変条件13〜16 のオラクル（§8、MISSION §1 の1）

- **条項**：MISSION §1 の1「spec §8 の不変条件は全部オラクルにする」。v2.0 で13〜16を足した。
- **現状**：
  - 13（決めるのはサイトだけ）は BLK-1、15（人のデータは持たない）は PRIV-4 が受ける。
  - 14（信用は売らない。Depth はお金で上がらない）と、16（ページの中で AI に問いかけない）を測るオラクルがない。
- **提案**：
  - 14：名簿の Depth の算出が、支払いの状態を入力に持たないことを確かめる。
  - 16：Gate とサイトが、応答の本文に AI 向けの指示文を差し込まないことを確かめる（人間の経路の差分0の GATE-1 を、自動化への応答にも広げる）。
  - 足してよいか。

## D. CLAUDE.md と MISSION.md

### D1. CLAUDE.md の冒頭の一文
