## 3. 朝に見てほしい判断

1. **DIV-7 の比べ方**：相手は、エージェント自身のオリジンの Date ヘッダー（外の時刻のサービスは足さない）。Date ヘッダーが無ければ「比べられなかった」と言うだけ。問題にするのは、往復と秒の切り捨ての誤差を引いても ±30秒を越える時だけ。
2. **spec §12.9「初回の鍵の取得中は Pressure 0〜1 なら通す」は入れていない**（コードフリーズ中に Gate の通り道を変えない）。試しに入れてみた（`discoveryDeadline` を P0〜1 で0にする1行。手元で全オラクル、PR にはしていない）：15件が落ちた（SEED-2、STD-3、GATE-5、GATE-7、GATE-10、DIV-1〜4、PUB-1、NEUT-1、WEB-13、PILOT-1、ONE-3、BLK-1。速い回では PUR-1 も）。どれも、初めて来たエージェントの1回目が UNVERIFIED になるため（GATE-7 と GATE-10 は攻撃のコーパスの期待も変わる）。Windows では、裏で続く鍵の取得がテストの終わりと重なり、libuv のアサーションで落ちたこともあった。今の害は、遅い鍵の一覧を持つエージェント自身の要求が最大 2.75 秒待つことだけ（人間は待たない）。ローンチの前に入れるか、後にするかを決めてほしい。
3. **壁（`wall`、Pressure 1）は、摩擦がつながっていないと効かない**（Node で `onFriction` が無い時、Next.js と Workers はいつも）。なのに記録とレポートは「既存の摩擦がかかった」と言う。spec は `friction_hook` の意味を決めていないので、直していない。案：つながっていない Gate は壁を「通した」として記録し、起動時に1行で警告する（ONE-3 の対に、つながっていない壁を仕込む）。影響の見積もり：`decide()` を変えず記録の時だけ変えるなら、`friction` を確かめているテストは `decide()` の純粋なテストとレポートのフィクスチャだけで、ONE-3 は `onFriction` をつなぐので変わらない。ただ、朝のレポートの「決めること」が、もう書いた壁をもう一度勧めてしまうので、レポートにも「壁はあるが、摩擦につながっていない」を出す必要がある。
4. **Durable Object の一括の操作は128件まで**とみなして、掃除を128件ずつにした。手元の workerd は300件を通した。本番の上限の資料は夜は読めないので、安全な方に倒した。
5. **REG-7 の「連絡先ごとに1日5件」は、他人のメールで使い切れる**。LEAK-1 のあと名簿は連絡先を持たず確かめもしないので、自分で作った Root で他人のメールを書いた登録を5回送れば、そのメールの持ち主は1日、そのメールでは登録できない（連絡先を書かなければ登録できる）。#141 のあと、`--contact` を書かない init は連絡先を送らないので、当たるのはメールを書いた登録だけ。上限を緩めるのは人間の判断なので、そのままにした。案：連絡先ごとの上限を外す（IP ごとと全体は残す）か、越えた連絡先は数えずに捨てて登録は通す。
6. **REG-7 の「IP ごとに1時間10件」は、NAT の後ろでは足りないかもしれない**。携帯の CGNAT や大きな会社の NAT は、1つのアドレスを多くの人で使う。HN の当日に同じ時間に試す人が多いと、11人目から1時間 429 になる。数字は `services/registry/wrangler.json` の `REGISTRY_LIMITS`（レーン3の持ち物）。上げるかは人間の判断なので、そのままにした。
7. **レーン3の改名と、夜の diver の変更**：レーン3は `packages/diver/bin/ludion.mjs` と `doctor.test.mjs` を手元で直している（10-05 の main から）。夜にそこが変わった（#130、#141、#144）。新しい文言 `npx ludion doctor` と `npx ludion register` はテストがそのまま照合しているので、改名では文言とテストの期待を一緒に直すことになる。STATE.md に書いた。
